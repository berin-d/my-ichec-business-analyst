TP 4 : API REST et Authentification JWT

Contexte

Votre application est fonctionnelle, sécurisée et persistante. Mais elle ne communique qu'avec un navigateur via du HTML.

Dans ce TP, vous allez ouvrir FeatureHub au monde extérieur en exposant une API REST complète (filtrage, pagination, tous les verbes HTTP) et la protéger avec des tokens JWT.

Objectifs

  1. Implémenter des filtres et tris dynamiques sur la page d'accueil.
  2. Exposer les données via une API REST versionnée (/api/v1/) respectant les conventions REST.
  3. Implémenter le CRUD complet via l'API : GET, POST, PUT, PATCH, DELETE.
  4. Sécuriser les opérations d'écriture avec des tokens JWT (Bearer Token).

Exercice 2 : Blueprint API et Endpoints de Lecture (GET)

Tâche : Exposer les données de FeatureHub via une API REST versionnée en JSON, dans un Blueprint dédié.

REST (Representational State Transfer) repose sur des conventions : les ressources sont identifiées par des URI (/api/v1/features), manipulées via les verbes HTTP (GET pour lire, POST pour créer, etc.), et les réponses utilisent des codes de statut standard (200, 201, 404...).

Instructions :

  1. Blueprint : Créez app/api/routes.py avec un Blueprint api préfixé par /api/v1. Enregistrez-le dans create_app().

Versioning : Le préfixe /v1/ permet de faire évoluer l'API sans briser les clients existants. Si demain vous changez le format des réponses, vous créez /api/v2/ pendant que /api/v1/ continue de fonctionner.

  1. Méthode to_dict() : Dans votre modèle FeatureRequest, ajoutez une méthode qui convertit l'objet en dictionnaire :
def to_dict(self):
    return {
        'id': self.id,
        'title': self.title,
        'description': self.description,
        'status': self.status,
        'nature': self.nature,
        'priority': self.priority,
        'created_at': self.created_at.isoformat(),
        'author': self.author.username if self.author else None
    }
  1. Fonction d'erreur structurée : Créez une fonction utilitaire pour retourner des erreurs cohérentes. Les clients de votre API ont besoin de réponses toujours en JSON, jamais en HTML — même en cas d'erreur.
def make_error(status_code, message, field=None):
    response = {'error': message, 'code': status_code}
    if field:
        response['field'] = field
    return jsonify(response), status_code
  1. GET /api/v1/features : Créez une route qui retourne la liste avec filtrage, tri et pagination :
@api.route('/features')
def get_features():
    # Filtrage
    nature = request.args.get('nature')
    status = request.args.get('status')
    # Tri
    sort = request.args.get('sort', 'created_at')
    order = request.args.get('order', 'desc')
    # Pagination
    page = request.args.get('page', 1, type=int)
    per_page = request.args.get('per_page', 10, type=int)

    query = FeatureRequest.query
    if nature:
        query = query.filter_by(nature=nature)
    if status:
        query = query.filter_by(status=status)

    column = getattr(FeatureRequest, sort, None)
    if column:
        query = query.order_by(column.desc() if order == 'desc' else column.asc())

    pagination = query.paginate(page=page, per_page=per_page, error_out=False)
    return jsonify({
        'total': pagination.total,
        'page': pagination.page,
        'pages': pagination.pages,
        'per_page': pagination.per_page,
        'data': [f.to_dict() for f in pagination.items]
    })
  1. GET /api/v1/features/<int:id> : Retournez une seule demande ou une erreur 404 en JSON :
@api.route('/features/<int:id>')
def get_feature(id):
    feature = FeatureRequest.query.get(id)
    if not feature:
        return make_error(404, 'Demande introuvable')
    return jsonify(feature.to_dict())
  1. Testez dans le navigateur : http://localhost:5000/api/v1/features et http://localhost:5000/api/v1/features?nature=Bug&page=1&per_page=5.

Exercice 4 : Mettre à Jour une Ressource (PUT et PATCH)

Tâche : Implémenter les deux méthodes de mise à jour et comprendre leur différence fondamentale.

PUT remplace entièrement la ressource : tout champ non fourni revient à sa valeur par défaut. PATCH modifie partiellement : seuls les champs fournis sont mis à jour, les autres restent inchangés.

Instructions :

  1. PUT /api/v1/features/<int:id> — Remplacement total :
@api.route('/features/<int:id>', methods=['PUT'])
def update_feature_put(id):
    feature = FeatureRequest.query.get(id)
    if not feature:
        return make_error(404, 'Demande introuvable')

    data = request.get_json() or {}
    if not data.get('title'):
        return make_error(400, 'Le titre est requis pour un remplacement complet', 'title')

    # Le PUT écrase tout. Ce qui n'est pas fourni revient à la valeur par défaut.
    feature.title = data['title']
    feature.description = data.get('description', '')
    feature.nature = data.get('nature', 'Feature')
    feature.priority = data.get('priority', 'Moyenne')
    feature.status = data.get('status', 'En attente')

    db.session.commit()
    return jsonify(feature.to_dict())
  1. PATCH /api/v1/features/<int:id> — Modification partielle :
@api.route('/features/<int:id>', methods=['PATCH'])
def update_feature_patch(id):
    feature = FeatureRequest.query.get(id)
    if not feature:
        return make_error(404, 'Demande introuvable')

    data = request.get_json() or {}

    # Le PATCH ne modifie que ce qui est fourni
    if 'title' in data:
        feature.title = data['title']
    if 'description' in data:
        feature.description = data['description']
    if 'priority' in data:
        feature.priority = data['priority']
    if 'status' in data:
        feature.status = data['status']

    db.session.commit()
    return jsonify(feature.to_dict())
  1. Vérifiez la différence avec ces deux tests : - Envoyez un PATCH avec uniquement {"status": "Validé"} → vérifiez que le title n'a pas changé. - Envoyez un PUT avec uniquement {"title": "Nouveau titre"} → vérifiez que description est devenu "" et priority est revenu à sa valeur par défaut.

Exercice 5 : Suppression et Authentification JWT

Tâche : Implémenter la suppression d'une ressource et protéger toutes les opérations d'écriture avec des tokens JWT.

Pourquoi JWT et non Flask-Login ? Flask-Login s'appuie sur les cookies et maintient un état côté serveur — ce qui viole le principe stateless de REST. Un client mobile ne gère pas les cookies de la même façon qu'un navigateur. Avec les tokens JWT, l'état est entièrement côté client : chaque requête est autonome et contient ses propres credentials dans le header Authorization.

Partie A : Configurer Flask-JWT-Extended

  1. Installez la librairie : pip install Flask-JWT-Extended. Mettez à jour requirements.txt.

  2. Dans create_app(), configurez l'extension :

from flask_jwt_extended import JWTManager

app.config['JWT_SECRET_KEY'] = 'changez-moi-en-production'
jwt = JWTManager(app)

Partie B : Route de login (obtention du token)

  1. Créez la route POST /api/v1/auth/token dans votre Blueprint api :
from flask_jwt_extended import create_access_token
from app.models import User
from werkzeug.security import check_password_hash

@api.route('/auth/token', methods=['POST'])
def get_token():
    data = request.get_json() or {}
    username = data.get('username')
    password = data.get('password')

    user = User.query.filter_by(username=username).first()
    if not user or not check_password_hash(user.password_hash, password):
        return make_error(401, 'Identifiants invalides')

    token = create_access_token(identity=username)
    return jsonify(access_token=token), 200

Partie D : Implémenter DELETE

  1. DELETE /api/v1/features/<int:id> — Supprime la ressource et retourne 204 No Content (succès sans corps de réponse) :
@api.route('/features/<int:id>', methods=['DELETE'])
@jwt_required()
def delete_feature(id):
    feature = FeatureRequest.query.get(id)
    if not feature:
        return make_error(404, 'Demande introuvable')
    db.session.delete(feature)
    db.session.commit()
    return '', 204

Pourquoi 204 et pas 200 ? Le code 200 implique un corps de réponse. Après une suppression, il n'y a plus rien à retourner. Le code 204 signifie "succès, mais pas de contenu".

Partie E : Tester le flux complet

  1. Testez avec curl en trois étapes :

curl -X POST http://localhost:5000/api/v1/features \
