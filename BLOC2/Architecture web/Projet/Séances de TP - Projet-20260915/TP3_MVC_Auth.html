TP 3 : Architecture et Sécurité

Contexte

Votre application fonctionne, mais tout le code est dans un seul fichier app.py et n'importe qui peut ajouter, modifier ou supprimer des demandes. Dans ce TP, vous allez d'abord restructurer l'application selon le pattern MVC avec les Blueprints Flask, puis sécuriser l'accès en ajoutant un système d'inscription et de connexion.

Objectifs

  1. Restructurer l'application en modules (Application Factory, Blueprints, models.py).
  2. Mettre en place Flask-Login et gérer les utilisateurs.
  3. Créer les routes Register / Login / Logout.
  4. Adapter l'interface selon l'état de connexion.
  5. Lier les tables User et FeatureRequest (Relation One-to-Many).
  6. Protéger les routes et vérifier les permissions.

Exercice 1 : Refactorisation de l'Architecture (MVC, Factory et Blueprints)

Tâche : Séparer le code monolithique en modules selon le pattern Model-View-Controller (MVC) : les modèles dans leur fichier, les routes dans des Blueprints, et la création de l'application dans une Factory.

Instructions :

  1. Structure du projet : Créez un package app/ à la racine de votre projet avec l'arborescence suivante :
featureHub_app/
├── run.py                  # Point d'entrée
├── app/
│   ├── __init__.py         # Application Factory
│   ├── models.py           # Modèles SQLAlchemy
│   ├── main/
│   │   └── routes.py       # Blueprint principal (index, view, edit, delete)
│   ├── templates/
│   │   ├── base.html
│   │   ├── main/           # Templates du blueprint main
│   │   │   ├── index.html
│   │   │   ├── view_feature.html
│   │   │   └── ...
│   │   └── auth/           # Templates du blueprint auth (exercice 3)
│   └── static/
│       └── css/
  1. Modèles (app/models.py) : Déplacez votre classe FeatureRequest et l'instance db = SQLAlchemy() dans ce fichier. Attention : db est créé sans l'application (pas de SQLAlchemy(app)), il sera lié plus tard via db.init_app(app).
  2. Application Factory (app/__init__.py) : Définissez une fonction create_app() qui :
    • Crée l'instance app = Flask(__name__).
    • Configure la SECRET_KEY et la SQLALCHEMY_DATABASE_URI.
    • Initialise la base de données : db.init_app(app).
    • Crée les tables si elles n'existent pas encore, dans un contexte applicatif explicite :
with app.app_context():
    db.create_all()

Pourquoi app_context ? Flask-SQLAlchemy a besoin de savoir à quelle application il est rattaché pour accéder à la configuration (URI, etc.). En dehors d'une requête HTTP, ce contexte n'existe pas automatiquement : il faut le créer manuellement avec with app.app_context(). Sans cela, tout appel à db lèvera une erreur RuntimeError: No application found.

- Enregistre les Blueprints.
- Retourne l'instance `app`.
  1. Blueprint principal (app/main/routes.py) : Créez un Blueprint nommé main et déplacez-y toutes vos routes actuelles (index, add, view, edit, delete), en remplaçant @app.route par @main.route.
  2. Point d'entrée (run.py) : À la racine du projet, créez le fichier de lancement :
from app import create_app

app = create_app()

if __name__ == '__main__':
    app.run(debug=True)
  1. Mise à jour des url_for : Avec les Blueprints, tous les appels url_for doivent être préfixés par le nom du Blueprint. Mettez à jour vos templates :
<!-- Avant -->
<a href="{{ url_for('index') }}">Accueil</a>

<!-- Après -->
<a href="{{ url_for('main.index') }}">Accueil</a>
  1. Testez votre application pour vérifier que tout fonctionne comme avant.

Pourquoi cette restructuration ? C'est le pattern MVC (Model-View-Controller) : les modèles gèrent les données (models.py), les vues sont les templates Jinja2 (templates/), et les contrôleurs sont les routes Flask (routes.py). Séparer ces responsabilités rend le code maintenable et facilite le travail en équipe.

Exercice 2 : Le Modèle Utilisateur

Pourquoi a-t-on besoin de tout ça ? HTTP est un protocole sans état (stateless) : chaque requête est indépendante, le serveur ne se souvient pas de la précédente. Pour reconnaître un utilisateur entre deux requêtes, on utilise un cookie de session — le serveur y stocke un identifiant chiffré. Flask-Login gère ce mécanisme automatiquement : à chaque requête, il lit le cookie, charge l'utilisateur correspondant depuis la base de données, et le rend disponible via current_user.

Tâche : Préparez la base de données pour accueillir des utilisateurs, avec un hachage sécurisé des mots de passe.

Instructions :

  1. Dans app/models.py, créez une classe User héritant de UserMixin (fourni par Flask-Login) et de db.Model :
    • id : Integer, Primary Key.
    • username : String(80), Unique, non nullable.
    • password_hash : String(128).

UserMixin fournit automatiquement les propriétés requises par Flask-Login : is_authenticated, is_active, is_anonymous et get_id(). Sans lui, Flask-Login ne pourra pas gérer vos utilisateurs.

  1. Ajoutez deux méthodes utilitaires au modèle User pour encapsuler la logique de hachage :
from werkzeug.security import generate_password_hash, check_password_hash

def set_password(self, password):
    self.password_hash = generate_password_hash(password)

def check_password(self, password):
    return check_password_hash(self.password_hash, password)
  1. Callback user_loader : Dans app/__init__.py, configurez LoginManager et définissez la fonction qui permet à Flask-Login de recharger un utilisateur depuis la base de données à chaque requête :
from flask_login import LoginManager

login_manager = LoginManager()

def create_app():
    # ... configuration existante ...
    login_manager.init_app(app)

    @login_manager.user_loader
    def load_user(user_id):
        return User.query.get(int(user_id))
  1. Mettez à jour votre base de données (supprimez le .db et relancez pour recréer les tables).

Exercice 3 : Inscription et Connexion

Tâche : Permettre aux visiteurs de se créer un compte et de se connecter.

Instructions :

  1. Blueprint Auth : Créez un fichier app/auth/routes.py avec un Blueprint nommé auth. Enregistrez-le dans create_app().
  2. Configuration de la redirection : Dans create_app(), indiquez à Flask-Login où rediriger les utilisateurs non connectés :
login_manager.login_view = 'auth.login'
login_manager.login_message = 'Veuillez vous connecter pour accéder à cette page.'
login_manager.login_message_category = 'warning'
  1. Route Register (/register) :
    • En GET : Affichez un formulaire (Username, Password, Confirmation du password) dans templates/auth/register.html.
    • En POST : Validez les données (username non vide, mot de passe de 4 caractères minimum, confirmation identique). Si le username existe déjà, affichez un flash d'erreur. Sinon, créez le User en utilisant set_password() et sauvegardez-le en base.
  2. Route Login (/login) :
    • En GET : Affichez un formulaire de connexion dans templates/auth/login.html.
    • En POST : Cherchez le user par username. Vérifiez le mot de passe avec check_password(). Si OK, connectez-le avec login_user(user) et redirigez vers l'accueil. Sinon, affichez un flash d'erreur.
  3. Route Logout (/logout) :
    • Appelez logout_user(), affichez un flash de confirmation et redirigez vers l'accueil.

Exercice 4 : Navbar Dynamique (Authentification)

Tâche : Adapter la barre de navigation selon l'état de connexion de l'utilisateur.

Instructions :

  1. Dans base.html, utilisez current_user.is_authenticated pour afficher conditionnellement :
    • Si connecté : le nom d'utilisateur (current_user.username) et un lien "Déconnexion".
    • Si non connecté : des liens "Connexion" et "Inscription".

current_user est un objet global fourni par Flask-Login, accessible dans tous vos templates sans avoir besoin de le passer via render_template. Il représente l'utilisateur de la session en cours (ou un utilisateur anonyme si non connecté).

  1. Testez le flux complet : inscrivez un utilisateur, connectez-vous, vérifiez que la Navbar change, déconnectez-vous.

Exercice 5 : Relation Auteur-Demande

Tâche : Chaque demande doit appartenir à un utilisateur enregistré, et cette information doit être visible dans l'interface.

Instructions :

  1. Modèle : Dans app/models.py, modifiez FeatureRequest pour ajouter une clé étrangère author_id liée à user.id.
  2. Relation : Ajoutez une relation db.relationship dans User pour pouvoir accéder facilement à user.features, avec un backref='author' qui ajoute un attribut feature.author sur chaque demande.
# Dans User :
features = db.relationship('FeatureRequest', backref='author', lazy=True)

# Dans FeatureRequest :
author_id = db.Column(db.Integer, db.ForeignKey('user.id'))
  1. Contrôleur (app/main/routes.py) : Modifiez la route d'ajout (add_feature) :
    • Protégez-la avec le décorateur @login_required.
    • Lors de la création de la FeatureRequest, assignez automatiquement l'auteur : author_id=current_user.id.
  2. Templates : Sur les cartes de l'accueil et la page de détails, affichez le nom de l'auteur (ex: "Par {{ feature.author.username }}"). Gérez le cas où author est None (demandes créées avant l'ajout de cette relation).
  3. Recréez la base de données et testez.

Exercice 6 : Permissions (Protéger les Modifications)

Tâche : Un utilisateur ne doit pouvoir modifier ou supprimer que ses propres demandes. Les routes edit et delete créées au TP2 sont actuellement accessibles à tous.

Instructions :

  1. Protéger les routes : Ajoutez le décorateur @login_required sur les routes /feature/<id>/edit et /feature/<id>/delete.
  2. Vérifier l'auteur : Dans ces routes, après avoir récupéré la demande, vérifiez que feature.author_id == current_user.id. Si ce n'est pas le cas :
    • Affichez un message flash d'erreur (ex: "Vous n'avez pas la permission de modifier cette demande.").
    • Redirigez vers la page de détails ou l'accueil.
  3. Templates : N'affichez les boutons "Modifier" et "Supprimer" que si l'utilisateur connecté est le propriétaire de la demande :
{% if current_user.is_authenticated and current_user.id == feature.author_id %}
    <a href="{{ url_for('main.edit_feature', id=feature.id) }}" class="btn btn-warning">Modifier</a>
    <!-- Bouton supprimer... -->
{% endif %}

Authentification vs Autorisation : ces deux concepts sont distincts. L'authentification vérifie qui est l'utilisateur (Flask-Login, login_user). L'autorisation vérifie ce qu'il a le droit de faire (vérification author_id == current_user.id). @login_required gère l'authentification, mais c'est à vous de coder la logique d'autorisation.
